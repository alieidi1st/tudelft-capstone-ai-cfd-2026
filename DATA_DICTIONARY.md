# Data dictionary

Everything in `data/` is generated by `tools/build_dataset.py` from the raw CFD
sensitivity-analysis archive. All files are plain CSV with a header row.
`data/` is disposable: delete it and re-run the build script to get it back.

---

## 1. The experiment behind the data

Five independent studies were run with the **SST k–omega** turbulence model:

| case | geometry | Reynolds number | simulations |
|---|---|---|---|
| `channel_flow/Re_tau_180`  | plane channel | Re_tau = 180  | 1408 |
| `channel_flow/Re_tau_395`  | plane channel | Re_tau = 395  | 1408 |
| `channel_flow/Re_tau_640`  | plane channel | Re_tau = 640  | 1408 |
| `channel_flow/Re_tau_1020` | plane channel | Re_tau = 1020 | 1408 |
| `annular_flow`             | gap between a rod and an outer cylinder | single | 1408 |

In each study the nine turbulence-model parameters were sampled 1408 times and a
CFD simulation was run for every sample. **Re_tau = 640 is the reference case**
and the recommended starting point.

## 2. `turbulence_parameters.csv`

One row per parameter.

| column | meaning |
|---|---|
| `parameter` | name used as a column header everywhere else |
| `symbol` | LaTeX symbol, for plots |
| `description` | what the coefficient does in the turbulence model |
| `nominal` | the standard literature value |
| `lower_bound`, `upper_bound` | the interval it was sampled from |

The bounds are Table 1 of Eidi & Dwight (2026) and are what you pass to SALib as
the `problem` dictionary (`capstone_tools.make_salib_problem()` builds it).

## 3. `parameters.csv` (one per case)

The sampled parameter values: 1408 rows.

| column | meaning |
|---|---|
| `case_id` | `case_0000` … `case_1407`, the simulation identifier |
| `design_group` | **0–127. See the warning below.** |
| the nine parameter names | the value used in that simulation |

### The `design_group` column — read this before you split the data

The 1408 samples are **not** independent random draws. They are a *Saltelli
design*: 128 base samples, each expanded into a block of 11 rows
(`1408 = 128 x (9 + 2)`). Inside a block, 9 of the rows differ from the base row
in **exactly one** of the nine parameters. That structure is what makes the Sobol
estimator work, but it has a consequence for machine learning:

> If you split rows at random, almost every test simulation has a near-twin in the
> training set differing in one coordinate out of nine. Your model will predict
> those nearly perfectly and your test score will be far too optimistic.

`design_group` identifies the block. Keep a whole block on one side of the split,
for example with `sklearn.model_selection.GroupShuffleSplit` or `GroupKFold`.
On this dataset the difference is about 0.99 versus 0.96 in test R^2 — not
catastrophic, but enough to matter, and the grouped number is the honest one.

## 4. `profile_<variable>.csv` (one per case per variable)

A 1408 x 40 table: one row per simulation, one column per position across the
flow.

| column | meaning |
|---|---|
| `case_id` | matches `parameters.csv` |
| `point_00` … `point_39` | the variable at that position |

Two variables are provided. **Two variables x 40 positions = the 80 CFD
outputs** referred to in the project description.

| file | symbol | quantity |
|---|---|---|
| `profile_p_rms.csv` | p'_rms | pressure-fluctuation intensity — drives vibration and fatigue |
| `profile_k.csv` | k | turbulent kinetic energy |

### What exactly is in the pressure column

The two flow cases were post-processed differently in the published study, and
the files reproduce that exactly so that the benchmark indices match the paper:

* **channel flow** — `p_rms` is the root-mean-square pressure fluctuation divided
  by a reference `u_tau^2` (see the units caveat below), i.e. a dimensionless
  intensity of order 1–3;
* **annular flow** — `p_rms` is the *mean square* pressure fluctuation
  (`pfluctSqrMean`) in m^2/s^2, which is the quantity the published annular
  sensitivity analysis was run on.

The two are therefore related by a square, not identical. This does not matter
within a case — you always analyse one case at a time — but do not compare the
absolute numbers between the channel and the annular case.

## 5. `profile_coordinates.csv` (one per case)

Where the 40 points are.

Channel flow: `point_index`, `y_plus`, `y_metres`.
Annular flow: `point_index`, `wall_distance_metres`.

### Units caveat for the channel case — please read

The raw extraction normalised **all four Reynolds numbers** with a single
reference friction velocity, `u_tau_ref = 0.0128 m/s`, and a single viscosity,
`nu = 2e-5 m^2/s`. The mesh is identical in all four cases, so:

* `y_plus = y_metres * u_tau_ref / nu = y_metres * 640` for every case;
* `p_rms` is divided by `u_tau_ref^2` in every case.

This means `y_plus` and the "wall units" are **physically correct only at
Re_tau = 640**. At the other three Reynolds numbers the same constant was used,
so those columns are a consistent *scaled* coordinate rather than true wall
units.

This does **not** affect any result in this project. Sobol indices, permutation
importance and SHAP rankings are all unchanged when an output is multiplied by a
constant, so every sensitivity conclusion is unaffected. It only matters if you
want to interpret the absolute numbers physically, or compare magnitudes between
Reynolds numbers — in which case say clearly that the scaling is a fixed
reference, not per-case wall units.

## 6. `scalar_outputs.csv` (one per case) — the recommended starting point

This is the **reduced starter dataset**. It joins the parameters to six single
numbers derived from the 40-point profiles, so you can run a complete
regression-and-explanation workflow on one well-behaved target.

Columns: `case_id`, `design_group`, the nine parameters, then

| output | definition |
|---|---|
| `p_rms_peak` | maximum of the p_rms profile |
| `p_rms_wall` | p_rms at the point nearest the wall |
| `p_rms_integral` | p_rms integrated across the profile (trapezoid rule) |
| `k_peak` | maximum of the k profile |
| `k_centre` | k at the last point (channel centre-line / outer edge of the gap) |
| `k_integral` | k integrated across the profile |

`k_centre` is the interesting one: it is the only output for which a third
parameter (`alphaK1`) becomes non-negligible.

## 7. `sobol_benchmark/` — the answer you are trying to reproduce

Computed with SALib from **all 1408 simulations**, for every output in this
dataset. You never need to compute these yourself.

`channel_Re_tau_<Re>_scalar.csv` and `annular_scalar.csv`:

| column | meaning |
|---|---|
| `output` | one of the six scalar outputs |
| `parameter` | one of the nine parameters |
| `S1`, `S1_conf` | first-order index and its 95% confidence half-width |
| `ST`, `ST_conf` | total-order index and its confidence half-width |

`channel_Re_tau_<Re>_profiles.csv` and `annular_profiles.csv`: the same, with
`variable` and `point_index` instead of `output`, so there is a benchmark at
every one of the 80 outputs.

### How to read the indices

* **S1** — the fraction of the output variance caused by that parameter *alone*.
* **ST** — the same, *including* everything the parameter does in combination
  with others.

Permutation importance and SHAP both capture combined effects, so **ST is the
like-for-like comparison** and is the primary reference used in the notebooks.

`ST - S1` is the interaction part. On this dataset it is tiny: the indices sum to
about 0.99, so the response is nearly additive and S1 and ST almost coincide.

Indices can come out slightly negative. That is normal Monte-Carlo noise on an
index whose true value is zero; it means "no measurable effect".

### What the full study concluded

Only four of the nine parameters matter: **betaStar, alphaOmega1, beta1 and
kappa**. The published analysis reduced the problem to exactly that set. With
increasing Reynolds number the importance of alphaOmega1 grows while betaStar
shrinks, and in the annular geometry alphaOmega1 overtakes betaStar.

That is the conclusion your workflow should be trying to recover from a fraction
of the data.

## 8. `channel_flow/dns_reference_p_rms.csv`

High-fidelity DNS pressure fluctuations (`y_plus`, `p_rms_dns`), used in the
original study to validate the CFD. It plays **no part** in the sensitivity
analysis and you do not need it, but it is included so you can see how the CFD
ensemble brackets the reference data.
